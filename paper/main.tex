\title{Recovery That Re-Asks the Model:\\
Duplicate and Lost Side Effects in Crash-Recovered LLM Agents}
\author{Param Madan\\Northeastern University\\\texttt{madan.pa@northeastern.edu}}
\date{October 2026}

\begin{document}
\maketitle

\begin{abstract}
Durable-execution systems make crash recovery correct by replaying
deterministic code against recorded results. LLM agents break this premise:
the code that decides which side effects to perform is a model whose answer
is not reproducible across requests. We show that recovery schemes that
\emph{re-ask the model} for a decision the crashed process had already
received can execute side effects twice or, depending on the
idempotency-key scheme, silently drop them. We separate two design axes that
are usually conflated, \emph{recording granularity} (is the model's decision
durable before it is acted on?) and \emph{key derivation} (provider tool-call
id, argument hash, or position), and measure their interaction under a
physical after-effect crash in three pre-registered rounds (5,940 runs; three
task shapes; two open 3B models; three temperatures), including a crash-free
control. Against that control, turn recording with provider call ids added
82--97 percentage points of duplicate side effects in every task; argument
hashes added 80 points once the model wrote an argument itself; and position
keys added 8 points of silently lost effects in multi-effect turns. Under
step recording, failure rates after a crash were statistically
indistinguishable from crash-free runs in all nine task/key conditions. A survey of the official
documentation of 15 agent-framework configurations finds that the
durable-execution engines prescribe step recording, while agent-SDK session
stores and several quickstarts give turn recording or none, and no framework
names the provider's tool-call id as the idempotency key. We argue that recording the model's decision before
acting is a correctness requirement, not an optimization, and outline a
correctness condition for recovered agent runs.
\end{abstract}

\section{Introduction}

A customer-service agent looks up a case, decides to issue a \$25 service
credit, and calls the ledger. The ledger writes the credit. Before the
response reaches the agent, its process is killed. A recovery process starts
the turn over: it sends the same conversation to the model, the model decides
again to issue the credit, and the provider assigns the new tool call a new
identifier. If that identifier is the idempotency key, the ledger now holds
two credits.

Idempotency keys are the standard defense against retried side effects, but
a key identifies a \emph{decision}. When recovery causes the decision to be
made again, the key is made again too, and whether it matches depends on
whether the new decision is identical to the old one \emph{in whatever the key
scheme looks at}. Provider call ids are fresh on every request; argument
hashes change whenever the model writes any argument in its own words;
position-based keys break when the model changes the number or order of its
effects, and in that case they fail in the other direction, by suppressing a
legitimate effect.

\section{Background}
\paragraph{Durable execution.} Workflow engines make long-running programs
survive crashes by recording the result of every external call in a history
and, on recovery, re-running the orchestration code while substituting
recorded results for the calls it already made. Azure Durable Functions
formalizes these semantics~\cite{burckhardt2021durable}. DBOS builds the
same guarantee on a transactional database~\cite{skiadopoulos2021dbos}. Both
require the orchestration code to be \emph{deterministic}: re-running it must
reach the same calls in the same order, or the recorded history no longer
lines up.

\paragraph{Side effects and compensation.} A side effect that cannot be
rolled back is either made idempotent, deduplicated under a key, or undone by
a compensating action, as in sagas~\cite{garciamolina1987sagas}.
Exactly-once processing in stream systems rests on the same two pieces,
deterministic keys and durable records of what was
processed~\cite{akidau2013millwheel,carbone2017flink}.

\paragraph{Tool-calling agents.} An LLM agent alternates model calls, which
choose tool calls and arguments, with tool executions whose results go back
into the model's context~\cite{yao2022react}. Providers give every tool call
an identifier, which is fresh on every request. The control flow, the very
thing durable execution needs to be deterministic, is the model's output.

\section{A taxonomy of agent recovery}
\label{sec:taxonomy}

\paragraph{Recording granularity.} Under \emph{step} recording, every model
response, including the tool calls it chose, is durable before any of those
calls execute, and every tool result is durable when it returns. Recovery
reuses recorded responses and re-executes only calls whose results are
missing. Under \emph{turn} recording, state is persisted when a turn or run
completes; a crash inside the turn loses the model's decision, and recovery
asks the model again.

\paragraph{Key derivation.} \texttt{tool\_call\_id} uses the identifier the
model provider assigns to the call. \texttt{args\_hash} hashes the task id,
tool name, and canonicalized arguments. \texttt{position} combines the task
id, tool name, and the ordinal of that tool's call within the run.

\paragraph{Why step recording makes the key irrelevant.} Under step recording
the call being retried is the \emph{same recorded call}, so any deterministic
function of it (its provider id, its arguments, or its position) yields the
same key on retry. Under turn recording the retried call is a \emph{new}
decision, and exactly-once holds only when the new decision agrees with the
old one on every input to the key function.

\section{Method}
\label{sec:method}

\paragraph{Harness.} The tool server owns the ledger (ground truth), which
deduplicates by idempotency key. The after-effect fault: the server writes
the credit, then holds the response; the harness kills the agent process
with \texttt{SIGKILL}, releases the hold, and runs the agent's recovery (the
same command) once. Scoring reads only the ledger and an append-only
observation trace the agent never reads.

\paragraph{Study agent.} One neutral, roughly 200-line tool-calling agent
implements both granularities and all three key schemes, so the comparison is
between recording disciplines rather than products. The author also builds a
durable runtime (Aurelia) that uses step recording; that runtime is
deliberately \emph{not} a contestant.

\paragraph{Tasks.} \emph{credit}: one case, every tool argument copied from a
tool result. \emph{memo}: as credit, plus a required customer-facing reason
the model writes. \emph{two}: two cases in one request, order chosen by the
model.

\paragraph{Models and sampling.} \texttt{qwen2.5:3b} and
\texttt{llama3.2:3b} served by Ollama~0.32.5 at temperatures 0, 0.7, and 1.0.
The per-request seed differs between the crashed and the recovering
invocation, as in production, and is reproducible from the run seed.

\paragraph{Pre-registration.} Round~1 (credit, Apple~M1, serial; 1,080 runs),
Round~2 (all three tasks, one NVIDIA A100, 16 concurrent runs; 3,240 runs,
including a hardware replication of Round~1), and Round~3 (the Round~2 setup
with no fault; 1,620 runs) were each pre-registered with predictions,
outcomes, exclusions, and analysis before any measured run. Round~3 was
designed \emph{after} Round~2's results were seen, to separate model errors
from recovery errors, and its pre-registration says so. All predictions were
drafted with an AI coding assistant and approved unedited by the author. We
report every prediction, including falsified ones. Two analysis-only
amendments and one aborted, discarded Round~2 job (an inference-server
misconfiguration) are documented with timestamps that precede the data they
affect.

\paragraph{Outcomes.} \emph{Duplicate}: more than one ledger credit for a
case. \emph{Lost effect}: the run reports success but the ledger lacks a
credit for a named case. Rates are over runs in which the kill fired; runs in
which it did not are reported per cell. Intervals are Wilson
95\%~\cite{wilson1927}; differences between rounds use Newcombe's
interval~\cite{newcombe1998}.

\section{Results}
\label{sec:results}

\subsection{Model behaviour that limits what can be measured}
llama3.2:3b reached the fault in \emph{none} of its 540 Round~1 runs: it
usually wrote the tool call as plain text in the message
(\texttt{\{"name": "issue\_service\_credit", ...\}}) rather than as a
structured call, so no side effect happened and there was nothing to kill.
On the cluster it reached the fault in only 9 of 540 \emph{credit} runs, but
more often in \emph{two}. qwen2.5:3b reached the fault in 521 of 540
Round~1 runs; most of the 19 exclusions ended the turn without calling the
credit tool, in several cases telling the customer a credit identifier that
was never issued. \textbf{Round~1's conclusions therefore rest on
qwen2.5:3b alone.}

\subsection{Round 1: arguments copied from tool results}
All five pre-registered hypotheses that had data held
(Table~\ref{tab:r1}). Under turn recording with provider call ids, every
recovered run duplicated the credit (87 of 87 kill-triggered runs). Every
other granularity/key pair produced zero duplicates. Re-asking happened in
every turn-recorded recovery and in no step-recorded one. The
argument-hash and position keys survived re-asking here because the model
copied every argument from a tool result, so the repeated decision was
identical.

\subsection{Round 2: model-authored arguments and multi-effect turns}
Round~2 re-ran the credit task on the cluster. For qwen2.5:3b it reproduced
every Round~1 verdict. As written, the replication hypothesis (R2-H6) is
\textbf{falsified}: llama's few kill-triggered credit runs (cells with
$n \le 2$) flip two verdicts.

\paragraph{Argument hashes fail once the model writes an argument.} In
\emph{memo}, turn recording with \texttt{args\_hash} duplicated the credit in
53\%, 97\%, and 97\% of qwen's recoveries at $T = 0, 0.7, 1.0$
(Table~\ref{tab:r2dup}). The model rewrote the free-text \texttt{reason}, so
the hash changed. Our prediction R2-H2 (${\le}10\%$ at $T{=}0$) was
\textbf{falsified}: even at temperature zero, a re-asked model wrote a
different reason in 16 of 30 runs. Round~2 serves 16 concurrent requests per
GPU and changes the seed between invocations; this design cannot tell which
of the two causes the divergence. Position keys survived \emph{memo}
(R2-H3 held).

\paragraph{Position keys drop effects when the plan changes.} In \emph{two},
turn recording with \texttt{position} keys produced lost effects (R2-H4
held), most often with llama3.2:3b (Table~\ref{tab:r2lostllama3}). A
re-asked model took the cases in a different order, the ordinal key
collided with the recorded one, and the ledger dropped a real credit while
the run reported success. Argument hashes also duplicated in \emph{two}
(R2-H5 \textbf{falsified}: up to 68\% for qwen at $T{=}1$). In 35 of the 37
duplicated runs, the re-asked decision for an already-credited case carried
a \emph{different amount}; these 3B models often got amounts wrong.

\paragraph{Step recording: recovery was correct; the model was not.} R2-H1
predicted zero duplicates and zero lost effects under step recording. It was
\textbf{falsified}: 23 duplicates and 21 lost effects across all step
cells. In an exploratory look at all 44 runs, recovery re-executed the
recorded call under its \emph{recorded} key every time, and the ledger
deduplicated it. Every failure came from a \emph{later, new} decision by the
model: crediting a case again (often to correct an amount), or reporting
success for a case it never credited. H1 as written did not separate
recovery errors from model errors. Whether model errors are \emph{more
frequent} after a crash is measured by Round~3, a crash-free control
pre-registered after these results (\S\ref{sec:r3}).

\subsection{Round 3: crash-free control}
\label{sec:r3}
Round~3 ran the Round~2 agent, models, seeds, and hardware with no fault
(1,620 runs; 1,053 reached the credit tool). Table~\ref{tab:r3} compares each
recovered condition with its crash-free counterpart. All three
pre-registered hypotheses held.

\begin{itemize}
  \item \textbf{Step recording adds nothing measurable} (R3-H1). In all nine
        task/key cells, the 95\% intervals for both the duplicate and the
        lost-effect difference include zero. The model errors seen under
        step recording in Round~2 occur at the same rate when nothing
        crashes.
  \item \textbf{Turn recording adds duplicates} (R3-H2): $+97$, $+96$, and
        $+82$ points with provider ids in \emph{credit}, \emph{memo}, and
        \emph{two}; $+80$ and $+21$ points with argument hashes in
        \emph{memo} and \emph{two}.
  \item \textbf{Position keys trade duplicates for lost effects:} in
        \emph{two}, turn recovery with position keys adds $+8$ points of lost
        effects $[+2, +14]$ and no significant duplicates.
  \item Without a crash, argument hashes never duplicate more than provider
        ids (R3-H3): they deduplicate a model's identical repeat calls.
\end{itemize}

\paragraph{Turn vs.\ step, task \emph{two}.} Pooled over keys and
temperatures, qwen2.5:3b duplicated in 123 of 265 turn-recorded recoveries
versus 16 of 261 step-recorded ones; llama3.2:3b in 68 of 228 versus 4 of
235, with lost effects in 29 of 228 versus 17 of 235.

\section{What frameworks document}
\label{sec:survey}
We read the official documentation and official repositories of 15
agent-framework configurations on 2026-10-12, recording where each documented
durable pattern makes the model's tool-call decision durable, and what it
says about idempotency keys. The full table, quotations, and URLs are in
\texttt{docs/research/rq4-survey.md}.

\begin{itemize}
  \item \textbf{Step} is what the durable-execution engines and their agent
        integrations prescribe: Temporal (model and tool calls as separate
        activities), DBOS, Restate, Inngest, Pydantic~AI on those engines,
        the OpenAI Agents SDK with Temporal, and Google ADK with resumability
        enabled~\cite{doc_temporal_agentloop,doc_dbos_ai,doc_restate_agents,doc_adk_resume}. LangGraph reaches step through separate model and tool nodes
        and per-super-step checkpoints, guaranteed only in its
        \texttt{"sync"} durability mode~\cite{doc_langgraph_persistence}.
  \item \textbf{Turn} is what agent-SDK session stores give: OpenAI Agents
        SDK Sessions (``After each run'')~\cite{doc_openai_sessions}, AutoGen's manual
        \texttt{save\_state}~\cite{doc_autogen_state}, and Microsoft Agent Framework's workflow
        checkpoints for agent executors. Microsoft's Durable Task extension for
        Agent Framework ``internally implements entity-based agent loops,''
        in which ``the agent framework manages the loop; the entity provides
        session persistence'' and ``persists conversation state across
        interactions''~\cite{doc_msft_durable_agents,doc_msft_patterns}. The documentation does not describe recording the
        model's tool-call decisions \emph{within} an agent run. The same
        documentation also presents an orchestration-based loop that runs
        tool calls as activities, which is step-granular.
  \item \textbf{Quickstarts mostly give none or turn}, through in-memory
        stores or opt-in durability.
  \item \textbf{No framework names \texttt{tool\_call\_id} as the
        idempotency key}, the key that failed in every turn-recorded cell we
        measured. Temporal names run id plus activity id~\cite{doc_temporal_activity}; Restate names a
        journaled random UUID; most others say ``make tools idempotent''
        without naming a key.
\end{itemize}

\section{Discussion}
\paragraph{Recording the decision is the safeguard; the key is not.}
Across both rounds, every key scheme failed under turn recording on at least
one common task shape: provider ids always, argument hashes once the model
authors an argument, and position keys once the number or order of effects
can change. Under step recording, recovery never repeated or dropped a
decision. Frameworks that offer turn-level persistence for agents should say
in their documentation that it does not make tool side effects safe across a
crash, and should offer step recording for agents that write to the outside
world.

\paragraph{What step recording does not fix.} Step recording only prevents
the \emph{recovery} from re-making a decision. It cannot stop a model from
making a new, wrong decision later in the same run, and our 3B models often
did: repeated credits, wrong amounts, success reported for effects that
never happened. Those are errors of task correctness, and need checks at the
effect boundary, such as per-case ledger invariants or amount validation,
rather than a recovery mechanism. Round~3 shows that under step recording
these errors are no more frequent after a crash than without one.

\paragraph{Cost.} Step recording adds one durable write per model response
before its tool calls execute. We did not measure that cost here.

\paragraph{Toward a correctness condition.} A natural definition, modelled on
linearizability~\cite{herlihy1990linearizability}: a recovered run is
correct iff its history of external effects equals that of some crash-free
run of the same agent under the same recorded model outputs. We plan to
state this in TLA~\cite{lamport1994tla}, model-check the step protocol
against it, and check our durable runtime against the specification.

\section{Threats to validity}
Small open models; one domain; we implement the patterns frameworks
document rather than running every framework's code; Round~2 uses different
hardware and concurrent decoding (hence the replication task); the author
builds a step-recording runtime. Code, configuration, raw data, and both
pre-registrations are public.

\section{Related work}
Durable-execution semantics~\cite{burckhardt2021durable,skiadopoulos2021dbos}
assume deterministic orchestration. This paper measures what happens when the
orchestrator is a model and the assumption is dropped. Exactly-once stream
processing~\cite{akidau2013millwheel,carbone2017flink} gets its guarantee
from deterministic record identities, the property provider-assigned tool-call
ids lack. Sagas~\cite{garciamolina1987sagas} handle effects that cannot be
deduplicated. Our lost-effect results show that the wrong deduplication key
can do harm in the other direction, too. Agent benchmarks such as
$\tau$-bench~\cite{yao2024taubench} measure task success and consistency over
repeated trials. We measure a narrower property, side-effect correctness
under a physical crash, and separate model errors from recovery errors with
a crash-free control. The correctness condition we propose for future work is
modelled on linearizability~\cite{herlihy1990linearizability}, and we plan to
specify it in TLA~\cite{lamport1994tla}.
